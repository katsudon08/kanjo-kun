# /docs — ドキュメントの作成・更新・同期

## 役割
勘定くんの `docs/` 配下を、常にコードと実態に合った状態に保つ。新規作成・更新・相互の同期、および用語統一・ADR の追加を担う。

## 対象ドキュメント
- `docs/requirement.md`: 目的・背景・対象ユーザー・ユーザーストーリー・機能要件・マイルストーン。
- `docs/domain.md`: ドメイン用語集（唯一の用語の正）。
- `docs/architecture.md`: 技術スタック・構成・確定済みの技術方針（ADR の集約ビュー）。
- `docs/workflow.md`: 開発フロー（GitHub Flow、ブランチ命名、コミット規約等）。
- `docs/adr/NNNN-kebab-summary.md`: 個別の技術的意思決定記録。

## 前提
- 出力は日本語。
- 技術スタックは未確定。スタック固有の具体（コマンド・ライブラリ名・ディレクトリ構成等）を勝手に確定・捏造しない。未確定箇所は「（技術スタック決定後に記載 / docs/architecture.md 参照）」のプレースホルダにする。
- 用語は必ず `docs/domain.md` の用語集に統一する。新しい概念が出たら、まず用語集に定義を追加してから他ドキュメントで使う。

## 手順
1. 何を作成/更新/同期するか目的を確認する。コード変更に追従する場合は、対象の変更内容（差分・PR・機能）を把握する。
2. 関連する既存ドキュメントを読み、現状と整合性のずれを洗い出す。
3. 用語の揺れがあれば `docs/domain.md` を正として統一する。新語があれば用語集へ追記する。
4. 対象ドキュメントを作成/更新する。要件の意図を保ち、確定事項と未確定事項を区別して書く。スタック固有箇所はプレースホルダにする。
5. 相互同期を確認する。例: 機能追加で要件が変わったら `requirement.md`、用語が変わったら `domain.md` と参照箇所、技術判断が変わったら `architecture.md` と該当 ADR、開発手順が変わったら `workflow.md` を併せて更新する。
6. 変更は機能ブランチ（対応 issue があれば `docs/<issue番号>-<kebab要約>`、無ければ `docs/<kebab要約>`。詳細は docs/workflow.md「ブランチ命名規則」）で行い、`docs(scope): 日本語の要約` 形式でコミットする。main への直コミット/直push は禁止。

## ADR の追加手順（Nygard 形式）
1. 既存の `docs/adr/` を確認し、次の連番を決める（4桁ゼロ詰め）。ファイル名は `docs/adr/NNNN-kebab-summary.md`（4桁連番＋英語ケバブの要約。例 `0003-debt-graph-reduction-algorithm.md`）。要約は小文字 + ハイフンのケバブケースで簡潔に。
2. 本文は Nygard 形式の節で構成する（既存の ADR-0001 と表記を揃える）。
   - タイトル: `# ADR-NNNN: 決定の要約`（既存 ADR-0001 と同じ見出し形式）
   - ステータス: 提案 / 承認 / 却下 / 非推奨 / 〇〇により置換 のいずれか。
   - 文脈: 何を背景に、どんな制約・力学の中でこの判断が必要か。
   - 決定: 何を採用すると決めたか（能動形で簡潔に）。
   - 結果: 採用により生じる良い点・悪い点・今後の影響。
3. ADR を追加・変更したら `docs/architecture.md` の集約ビューに反映し、関連ドキュメントとの整合を取る。
4. 過去の決定を覆す場合は、旧 ADR のステータスを「〇〇（新番号）により置換」に更新し、新 ADR の本文から旧 ADR を参照する。

## 規約・注意
- 技術選定そのものの議論や計画立案は `/plan` の役割。本 skill は「決まったこと・要件・用語」をドキュメントとして残し同期することに専念する。
- コードレビューやアプリ動作確認は `/code-review` `/review` `/run` `/verify` が担う。本 skill はそれらを再実装しない。
- 未確定の技術スタックを断定的に書かない。プレースホルダと「要 ADR 化」を使い分ける。
