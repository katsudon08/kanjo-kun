## 役割
ワークツリーの変更内容を確認し、関連する変更を論理単位にまとめてステージングし、Conventional Commits 形式（日本語要約・日本語本文）でコミットする。1コミット1論理変更を徹底する。

## 前提
- 記述言語は日本語で統一する。コミットメッセージの type だけ英語、scope・要約・本文・footer はすべて日本語で書く。
- Git 運用は GitHub Flow。main への直コミットは禁止。コミットは必ず機能ブランチ上で行う。
- スタック固有のビルド/リンタ実行などはここでは行わない（必要な動作検証は /verify、コードレビューは /code-review を案内する）。

## 手順
1. `git status` で変更ファイル一覧を確認し、`git diff`（必要に応じて `git diff --staged`）で変更内容を把握する。何を・なぜ変えたのかを自分の言葉で要約できる状態にする。
2. `git branch --show-current` で現在のブランチを確認する。`main` だった場合はコミットを中止し、ユーザーに機能ブランチの作成を促す。ブランチ命名は `type/<issue番号>-<kebab要約>`（対応 issue がある場合。例: `feat/12-receipt-ai-input`）、対応 issue が無ければ `type/<kebab要約>`（例: `chore/setup-claude-env`）。詳細は docs/workflow.md「ブランチ命名規則」を参照。ユーザー合意のうえ `git switch -c <ブランチ名>` で作成してから先に進む。
3. 関連する変更だけを `git add <path>` でステージする。無関係な変更が混在する場合は、論理単位ごとに分けて複数回コミットする。`git add -A` の安易な利用は避け、ステージ内容を `git status` で再確認する。
4. コミットメッセージの1行目を `type(scope): 日本語の要約` の形式で生成する。type は下表から選ぶ。scope は任意で、本プロジェクトのドメイン（下記の scope 例）から小文字で選ぶ。要約は命令形に近い簡潔な日本語にする。
5. 本文（2行目以降、1行空けて記述）に「なぜその変更が必要か」を日本語で書く。「何を変えたか」は diff から分かるので、背景・意図・判断理由を中心に書く。関連 Issue があれば footer に `Closes #N` を付ける。破壊的変更がある場合は footer に `BREAKING CHANGE: 内容` を付ける。
6. `git commit -m "..." -m "..."` 等でコミットする。複数行メッセージはヒアドキュメント等で確実に渡す。コミット後 `git log -1 --stat` で内容を確認し、結果をユーザーに報告する。リモートへ反映する場合は /push を案内する。

### type 一覧表
| type | 用途 |
| --- | --- |
| feat | 新機能の追加 |
| fix | バグ修正 |
| docs | ドキュメントのみの変更 |
| style | 動作に影響しない整形（空白・フォーマット等） |
| refactor | 挙動を変えないリファクタリング |
| perf | パフォーマンス改善 |
| test | テストの追加・修正 |
| build | ビルドシステムや依存関係の変更 |
| ci | CI 設定・スクリプトの変更 |
| chore | その他の雑務（上記に当てはまらない変更） |
| revert | 過去コミットの取り消し |

### scope 例（任意・小文字のドメイン名）
`receipt`（レシート自動入力）, `member`（メンバー管理）, `settlement`（精算・債務簡約）, `flowchart`（フローチャート可視化）, `branch`（店舗ブランチ）, `payment-source`（支払い源）, `auth`（認証・権限）。該当が無ければ scope は省略してよい。

## 規約・注意
- main への直コミットは禁止。手順2のガードを必ず通す。
- 1コミットは1論理変更に保つ。巨大コミットや、無関係な変更をまとめたコミットは作らない。
- 秘密情報（APIキー、トークン、パスワード、`.env` の値、個人情報等）をステージ・コミットしない。`git diff --staged` で混入が無いか必ず確認する。
- 要約・本文・footer は日本語。type のみ英語。形式 `type(scope): 日本語の要約` を厳守する。
- **Co-Authored-By 等のトレーラ・署名（共著者表記・ツール署名など）は付与しない。** コミットだけでなく PR・issue でも同様に禁止する。
- ビルトイン skill と重複しない。動作検証は /verify、コードレビューは /code-review、PR 作成は /pr を案内する。
