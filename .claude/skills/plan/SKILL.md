# /plan — 実装計画の作成

## 役割
勘定くんの機能・タスクについて、着手前に「何を・どの順序で・どこに影響して・何をテストするか」を明文化した実装計画を作成する。コードは書かず、計画を出力することに専念する。

## 前提
- 出力は日本語。
- 技術スタック（FE/BE/言語/フレームワーク/DB/インフラ）は本リポジトリでは未確定。スタック固有の具体（コマンド・ライブラリ名・ディレクトリ構成等）を勝手に決め打ち・捏造しないこと。
- 技術選定は `docs/architecture.md` の決定（ADR）にのみ従う。ADR に記載がない事項は「未確定」として扱い、勝手に決めない。決める必要があれば計画内に「要 ADR 化」として論点を立てる。
- ドメイン用語は `docs/domain.md` の用語集に統一する（会計・店舗ブランチ・はしご・代表者・メンバー・支払い源・依存関係（債務グラフ）・フローチャート・割り勘比重・定数金額・精算・レシート自動入力）。

## 手順
1. 対象タスクの目的・スコープを確認する。曖昧なら計画作成前に利用者へ確認する。
2. `docs/requirement.md` を読み、対象機能の要件・マイルストーン上の位置づけ（MVP / 第1回 機能追加 / 第1回 リファクタリング）を把握する。
3. `docs/architecture.md`（および `docs/adr/` 配下の ADR）を読み、確定済みの技術方針を把握する。未確定箇所は「未確定」と明示する。
4. 必要なら内部で Plan サブエージェントを用い、要件と既存資料を突き合わせて計画案を生成する。
5. 次の構成で計画を出力する。
   - 概要: 対象タスクと達成したいゴール（1〜3行）。
   - 段階的ステップ: 着手順に並べた番号付きの作業ステップ。各ステップは1つの意味ある単位にする。
   - 影響範囲: 触れるドメイン領域・既存資料・他機能との関係（スタック固有のパスは「（技術スタック決定後に記載 / docs/architecture.md 参照）」とする）。
   - 検討事項・論点: 設計上の判断、トレードオフ、未確定で決めるべき点。技術選定が絡むものは「要 ADR 化」と明記する。
   - テスト方針: 何を・どの観点で検証するか（正常系/異常系、債務グラフの簡約結果・丸め・端数など勘定くん固有の注意点を含める）。具体的なテスト実行手順は確定後に `/verify` へ委譲する旨を添える。
   - 残し方の導線: 後述の「成果の残し方」を案内する。
6. MVP マイルストーンのタスク分解に使う場合は、`docs/requirement.md` のマイルストーン単位（店舗ブランチとフローチャート / メンバー管理 / FE・BE 作成 / 依存関係表示（権限別））でステップ群を切り、それぞれを独立着手可能な粒度に分解する。

## 成果の残し方（導線）
- 計画を作業チケットにする場合は `/issue` で GitHub Issue 化し、コミット footer で `Closes #N` を紐づける。
- 設計判断を恒久的に残す場合は `/docs` で `docs/` 配下（必要なら ADR）へ反映する。
- ブランチは `type/<issue番号>-<kebab要約>`（対応 issue があれば。例 `feat/12-receipt-ai-input`）／無ければ `type/<kebab要約>` で切る。詳細は docs/workflow.md「ブランチ命名規則」を参照。main への直コミット/直push は禁止。

## 規約・注意
- 計画段階ではコード・設定ファイルを生成しない。
- 未確定の技術スタックを前提にしたステップは書かない。前提を「要 ADR 化」として明示する。
- 動作検証は `/verify`、コードレビューは `/code-review`、PR レビューは `/review`、アプリ起動確認は `/run` が担う。本 skill はこれらを再実装せず、計画内で適切に案内する。
