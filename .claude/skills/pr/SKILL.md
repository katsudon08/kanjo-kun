## 役割
勘定くんリポジトリ（katsudon08/kanjo-kun）で、現在の機能ブランチから `main` 向けのプルリクエストを `gh pr create` で作成する。日本語のPRテンプレート本文を組み立て、`--body` で渡す。GitHub Flow（main + 機能ブランチ → PR でマージ）に則る。

## 前提
- gh CLI が認証済みであること（このリポジトリでは katsudon08 で認証済み）。
- ベースブランチは常に `main`。
- main への直push/直コミットは禁止。作業は機能ブランチ（命名: `type/<issue番号>-<kebab要約>`、例 `feat/12-receipt-ai-input`。詳細は docs/workflow.md「ブランチ命名規則」）で行う。
- コミット規約は Conventional Commits（`type(scope): 日本語の要約`）。

## 手順
1. 現在のブランチと状態を確認する。
   - `git branch --show-current` で現在ブランチを取得。`main` だった場合は中止し、機能ブランチへ切り替える（または新規作成する）よう案内する。main へPRを向けるのであって main から作らない。
   - `git status --porcelain` で未コミットの変更がないか確認。未コミット変更があればコミットを促す（コミット手順は /commit を案内）。
2. 未push変更の確認。
   - `git status -sb` や `git log origin/<branch>..HEAD --oneline` 等でリモートに未反映のコミットがないか確認する。
   - ローカルにしか無いコミット、またはリモート追跡ブランチが未作成の場合は、先に push が必要。**この場合は /push を案内し、push 完了後に本手順へ戻る**。
3. 既存PRの有無を確認する。
   - `gh pr view --json number,url 2>/dev/null` で同ブランチに既存PRが無いか確認。既にあれば新規作成せず、そのURLを案内する（必要なら本文更新を提案）。
4. PR本文を組み立てる。
   - 直近のコミット履歴（`git log origin/main..HEAD --oneline`）と差分概要（`git diff --stat origin/main...HEAD`）から、下記テンプレを日本語で埋める。
   - 「## 関連 issue」には、対応する issue 番号があれば `Closes #N` を記載（複数可）。無ければ「なし」と書く。
   - 本文はテンプレートファイルではなく、ヒアドキュメント等で組み立てて `--body` に直接渡す。
5. PRを作成する。
   - `gh pr create --base main --head <現在ブランチ> --title "<日本語タイトル>" --body "<組み立てた本文>"` を実行する。
   - タイトルは原則コミット規約に倣う（例 `feat(receipt): レシートAI自動入力の会計JSON変換を追加`）。
   - 任意オプション:
     - WIP・早期共有なら `--draft` を付与（ドラフトPR）。
     - レビュアー（先輩エンジニア）をアサインする場合は `--reviewer <github-username>`。アサインするかはユーザーに確認する（開発体制は自分＋先輩の2名、役割は流動的）。
6. 作成後の案内。
   - 出力されたPRのURLを提示する。
   - レビューが必要なら、GitHub上のPRレビューは /review を、ローカルの差分に対するコードレビューは /code-review を案内する。
   - マージ後に改めてコード品質を点検したい場合も /code-review を案内する。

## PR本文テンプレート（--body に渡す全文）
```
## 概要
<このPRで何を・なぜ行ったかを日本語で1〜3文。背景や狙いを簡潔に>

## 変更点
- <主要な変更を箇条書き。ドメイン用語（会計/店舗ブランチ/はしご/代表者/メンバー/支払い源/依存関係/フローチャート/精算 等）を統一して使う>
- <変更点2>

## 関連 issue
- Closes #<N>
（対応するissueが無い場合は「なし」と記載）

## 動作確認
- <どう確認したかを日本語で。手順や結果>
- （技術スタック決定後に記載 / docs/architecture.md 参照）

## レビュー観点
- <レビュアーに特に見てほしい点。設計判断・トレードオフ・債務簡約ロジックの妥当性 等>
```

## 規約・注意
- 出力・本文・コメントはすべて日本語（コミット規約の type のみ英語）。
- ベースは必ず `main`。main から直接PRを作らない（必ず機能ブランチから）。
- スタック依存の記述（具体コマンド・ライブラリ・ディレクトリ構成）は決め打ち・捏造しない。未確定箇所は「（技術スタック決定後に記載 / docs/architecture.md 参照）」と書く。
- 未push変更があるまま PR を作らない。先に /push を案内する。
- ビルトイン skill を再実装しない。PRレビューは /review、ローカル差分のコードレビューは /code-review、動作検証は /verify、アプリ起動確認は /run を呼び出す/案内する側に寄せる。
