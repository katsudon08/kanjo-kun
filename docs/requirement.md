# 要件定義書 — 勘定くん

本書は「勘定くん」の要件を正式化したものである。記述は日本語で統一する。技術スタック（FE/BE/言語/フレームワーク/DB/インフラ）は未定であり、スタック依存の記述は「（技術スタック決定後に記載 / docs/architecture.md 参照）」のプレースホルダとする。

## 目的・背景

割り勘では、まず代表者がその場の支払いを立て替え、後からレシートを基に各自が代表者へ支払う、という流れになることが多い。これがはしご（複数店舗を巡る催し）になると会計が積み重なり、「誰が誰にいくら払うのか」という依存関係がごちゃごちゃになり、支払いがなぁなぁになってしまう。

勘定くんは、いつ・どこで・誰が・いくら払うのか（払うべきか）を分かりやすく可視化し、ことら送金や PayPay 等の送金サービスへ直接遷移して精算を完結できる形にすることを目的とする。

## 対象ユーザー

- 割り勘で金銭のやり取りをしっかりと行いたいユーザー。
- 飲み会の幹事で、お金の管理がうまくできていないユーザー。

## ユーザーストーリー

- 支払い代表者として、立て替えた会計の必要項目を入力したい。それにより、各メンバーが自分にいくら払うべきかを把握できる。
  - レシートからの自動入力はサブスクリプション機能として提供する。
- メンバーとして、代表者にいくら払うべきかを算出したい。それにより、適切な金額を迷わず送金できる。
- メンバーとして、代表者に支払った金額を入力したい。それにより、割り勘計算（残りの債務）を容易に把握できる。

## 機能要件

### 1. レシート自動入力（サブスク機能）

AI によりレシート画像を会計データ（JSON）へ変換する。会計の時間は文字列として扱う。

会計 JSON の例:

```json
{
  "店名": "居酒屋さくら 新宿店",
  "会計の時間": "2026-06-25 19:42",
  "会計時の金額": 12800,
  "メニュー": [
    { "品名": "生ビール", "単価": 600, "注文個数": 4 },
    { "品名": "枝豆", "単価": 400, "注文個数": 2 },
    { "品名": "唐揚げ", "単価": 700, "注文個数": 3 }
  ]
}
```

- 「会計の時間」は文字列（表示・記録用）とする。日時としての厳密なパース要否は今後検討する。
- AI 変換結果はユーザーが確認・修正できることを前提とする（誤認識の補正）。
- AI 変換の具体的な実装・モデル・API は（技術スタック決定後に記載 / docs/architecture.md 参照）。

### 2. 店舗ブランチとフローチャート

- はしご（イベント）を構成する各店舗訪問を「店舗ブランチ」として表現する。各店舗ブランチは1つの会計を内包する。
- 店舗ブランチは Git のブランチに着想を得た概念で、グループの分岐（一部メンバーが別の店へ移動）・合流をグラフ（合流は任意）として表す。各店舗ブランチはその店にいた参加メンバーを持ち、会計はその範囲で割り勘される。
- 店舗ブランチのグラフ構造と、それに紐づく金銭の流れをフローチャートとして可視化する。

### 3. 依存関係（債務グラフ）表示（権限別）

- フローチャートに基づき「誰が誰にいくら」を表す依存関係を表示する。
- 権限により表示範囲を切り替える。
  - 本人のみ表示: 自分が関わる債務のみを見る。
  - 全体一覧表示: 参加者全体の依存関係を見る（幹事・代表者向け等）。

### 4. メンバー管理

- 割り勘の参加者（メンバー）を登録・管理する。

### 5. 支払い源管理（単一/複数）

- 代表者が立替に用いた原資（支払い源）を管理する。
- 単一の支払い源だけでなく、複数の支払い源にまたがる立替も扱えるようにする。

### 6. 割り勘比重・定数金額管理

- 割り勘比重: 参加者ごとの負担割合を設定できる。
- 定数金額: 比重に依らない固定負担額を設定できる（例: 特定メンバーが特定品目を負担）。

### 7. 精算（送金サービスへの遷移）

- 算出された債務に基づき、ことら送金や PayPay 等の送金サービスへ直接遷移して精算を完結できる。
- 各メンバーが代表者へ支払った金額を入力し、残債を更新できる。

## 非機能要件

分かる範囲で記載する。不明な点は今後検討とする。

- 言語・記述: ドキュメント・UI 文言は日本語を基本とする。
- 精算ロジックの正確性: 「誰が誰にいくら」の債務グラフを、最小回数の送金へ簡約する（債務簡約）。端数処理の方針は今後検討する（合計が一致することを必須とする）。
- 権限・プライバシー: 依存関係の表示は権限（本人のみ/全体一覧）に応じて制御する。詳細な権限モデルは今後検討する。
- 可用性・性能・スケール: 具体目標値は今後検討する。
- セキュリティ: 送金サービス連携に伴う安全性要件は今後検討する（本アプリ自体は送金を代行せず、外部送金サービスへ遷移する想定）。
- プラットフォーム（Web/モバイル等）、認証方式、データ保持、課金（サブスク）基盤: いずれも未定。（技術スタック決定後に記載 / docs/architecture.md 参照）。
