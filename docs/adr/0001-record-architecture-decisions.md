# ADR-0001: アーキテクチャ上の意思決定を ADR として記録する

## ステータス

承認

## 文脈

勘定くんは、技術スタック（FE/BE/言語/フレームワーク/DB/インフラ）が未定の状態で開発を始める。今後、スタックの選定をはじめとして、ドメインモデルの構造、債務グラフの最小送金簡約アルゴリズム、権限モデル、外部送金サービス連携など、重要なアーキテクチャ上の意思決定が継続的に発生する。

2名体制（自分＋先輩エンジニア、役割は流動的）で開発するため、こうした意思決定の「何を・なぜ・どういう結果になるか」を後から追えるようにし、認識を揃えておく必要がある。意思決定の経緯が口頭やチャットに散逸すると、過去の判断の理由を見失い、再検討や引き継ぎのコストが大きくなる。

## 決定

アーキテクチャ上の意思決定を、ADR（Architecture Decision Record）として `docs/adr/` に記録する。

- 形式は Michael Nygard 形式に倣い、日本語で記述する。各 ADR は「タイトル / ステータス / 文脈 / 決定 / 結果」を持つ。
- ファイル名は `NNNN-kebab-summary.md`（4桁連番 + ケバブケースの要約）とする。本 ADR は `0001-record-architecture-decisions.md`。
- ステータスは「提案 / 承認 / 却下 / 非推奨 / 置換」等を用い、決定が変わった場合は新しい ADR を追加し、古い ADR のステータスを更新する（過去の ADR は削除せず履歴として残す）。
- ADR の追加・変更も GitHub Flow（PR 経由、`main` 直 push 禁止）に従って共有する。

## 結果

- 重要な意思決定の経緯（背景・理由・トレードオフ・結果）が `docs/adr/` に一元的に蓄積され、後から追跡・参照できる。
- 2名のチーム内で意思決定の認識を揃えやすくなり、引き継ぎや再検討のコストが下がる。
- ADR を書く運用上の手間が発生するが、判断の透明性と継続性のためにこれを受け入れる。
- 次の **ADR-0002** で、未定である技術スタック（FE/BE/言語/フレームワーク/DB/インフラ）の選定を記録する予定である。
